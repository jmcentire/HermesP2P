# Sandbox protocol contracts

These contracts describe **isolated executable reference models**, not production features. They do not connect to the website, a wallet, payment provider, blockchain, financial account, or network. Every unit is a dummy credit. The implementation is in `sandbox/credits.js`, `sandbox/signatures.js`, `sandbox/subscriptions.js`, and the application adapters in `sandbox/use-cases.js`. Run `node --test tests/sandbox*.test.js` with Node.js 22 or later.

The requirements come from the owner's current HP2P brief: transient anonymous gossip/ad hoc mesh, publicly routable bootstrap hubs followed by peer connections; optional caching/rebroadcast; publisher-only and symmetric subscription channels; monthly key rotation with negotiation one week either side of a month boundary; system-signed issuance and user-signed provenance; distinct advertising credits and signed evidence backchannel. These modules model only the credit and subscription contracts. They do not replace or claim to validate the transport. Private source histories are intentionally absent from this public document.

## Trust and state boundary

Stateless-by-design transport cannot by itself provide monetary conservation or finality. `DummyCreditAuthority` is one trusted, synchronous, **stateful in-memory** decision point. It stores unspent provenance references, issuance totals, redeemed totals, accepted-operation fingerprints and consumed claim IDs. Keys identify pseudonymous parties; they are not anonymous unlinkable credentials. Outputs, public keys, amounts, times, provenance and the authority's observation link activity.

A signature proves authorization by a key, not ownership of unspent value, human identity, human attention, ordering between disconnected recipients, revocation, or offline finality. A user-signed IOU is only an unaccepted proposal until the authority accepts it. The first valid spend processed by this single authority wins; this is **not** a claim about which recipient received it first. A 50-unit transfer consuming only 47 issued units fails entirely; the model does not choose which 47 of a competing 50 are honored.

The authority has no restart durability, distributed locking, consensus, key revocation, issuer-key rotation, authentication service, crash-safe settlement outbox or disaster recovery. Starting two authorities with the same issuer permits double spending across their separate states. A regression test deliberately demonstrates that failure. Production would require a chosen finality authority or consensus design, durable atomic transactions and retry records, and explicit privacy/censorship tradeoffs. A production service-redemption side effect would need an atomic outbox and receiver idempotency: the model only records dummy redemption, it does not deliver a service.

A compromised or colluding configured issuer can authorize arbitrary new dummy issuance up to the model's integer limit; supply conservation does not constrain that authority's minting policy. Key custody, recovery and revocation remain unresolved. Losing a private key can strand its unspent units; stealing one allows attempts to spend remaining units but does not erase accepted authority records. Compromised historical symmetric keys reveal their corresponding historical ciphertext; rotating future keys cannot undo that exposure. The injected clock is trusted authority/test input, not a client-supplied timestamp policy. Every authority operation observes a nondecreasing timestamp before other validation: even a rejected request can advance this clock watermark, but cannot change monetary state. A subsequent earlier timestamp fails before processing. This prevents reviving expired units by rolling the clock back; it does not protect against an untrusted caller supplying an arbitrarily far future time. Production must supply and persist authority-controlled time alongside durable state.

## Executable credit invariants

| ID | Contract | Executable surface |
| --- | --- | --- |
| C01 | Issuance requires the configured issuer's Ed25519 signature. Every amount is a positive safe integer; keys are canonical Ed25519 SPKI encodings. Unknown fields fail closed. | `issue`, `signatures` |
| C02 | Ordinary and advertising credits use distinct signature domains for issue, transfer, redeem, offer and claim. Currency cannot be relabeled or mixed within an input set. | `domain`, `transfer`, `reward` |
| C03 | A transfer consumes live, unspent provenance owned by its signer and produces exactly the same total. Duplicate inputs, missing inputs, wrong owners, fabricated units and arithmetic overflow fail before mutation. | `transfer` |
| C04 | For each kind, issued = outstanding + redeemed after every accepted or rejected operation. Outstanding includes expired unspent units, which remain unspendable. | `snapshot`; 600-step seeded adversarial simulation |
| C05 | Exact retries at nondecreasing authority time return the original immutable receipt, even after expiry. Operation IDs are scoped by signature domain (currency + action), signer and ID; different content under that same scope fails. Other signers/actions/currencies may reuse the ID without interference. Failed validation does not consume inputs, claim IDs or operation IDs; only the observed clock watermark may advance. | all authority operations |
| C06 | Redemptions consume each input at most once. Retrying the same redemption is safe; a differently identified duplicate fails. | `redeem` |
| C07 | Spending requires `now < expiresAt`; outputs inherit the earliest input expiry. Transfers and rewards cannot extend lifetime. Authority timestamps cannot move backward, including after a rejected expired request. | input validation, authority clock, transfer/reward outputs |
| C08 | Rewards consume only advertising credits, preserve advertising supply and return change to the advertiser. | `reward` |
| C09 | An advertiser-signed offer binds input provenance, recipient key, amount, expiry, requirements digest and challenge. The recipient-signed claim binds the exact signed offer digest, challenge and evidence digest. Accepted claim IDs are one-use per recipient signer; different recipients may reuse their own IDs. | `reward` |

An operation's output reference includes its operation ID, output index and a SHA-256 digest committing to the signed operation fingerprint. A transfer or redemption signs its input references. Signature domains include version, currency and action; publisher messages use a separate subscription domain. These are sandbox encodings, not a standardized production wire protocol or interoperability commitment.

The modeled advertising offer is recipient-specific, not a public auction or transferable reward. It does not reserve funds before a claim; a previously spent offer input fails at acceptance. The advertiser therefore checks settled funding before assuming payment can complete. Evidence is an opaque digest: **the model does not prove that video was viewed or attention occurred**. The closed campaign adapter below lets the advertiser collect signed claims for agreed actions, then pay participants from verified advertising units within a budget. Effectiveness remains an empirical question. Multiple pseudonyms, collusion and fabricated evidence may affect campaign quality, but cannot create extra model currency. The advertiser still must define which agreed action/evidence it accepts; any stronger human verification would introduce a separate privacy tradeoff.

The stated ordinary acquisition fee is approximately 5% (optionally volume-adjusted later), and the advertising acquisition fee is 20%. `FEE_BASIS_POINTS` records those baseline policy constants only. There is **no fee collection or conversion implementation**. The owner's $100 → 47-token example does not specify unit price, rounding, gross/net interpretation or volume schedule, so the test explicitly issues 47 dummy units; it does not invent an exchange rate. Fees do not establish legal or compliance immunity.

## Subscription contracts

| ID | Contract | Executable surface |
| --- | --- | --- |
| S01 | A publisher message verifies under the explicitly configured publisher key and binds channel, UTC month, message ID and text. | `publisherMessage`, `readPublisherMessage` |
| S02 | Symmetric messages use AES-256-GCM with a fresh random 96-bit nonce; channel, month and message ID are authenticated additional data. | `MonthlySymmetricChannel.seal/open` |
| S03 | Sending requires a configured key for the current UTC month. Reusing a key in a different month, or overwriting an epoch key, is rejected. | `addEpoch`, `seal` |
| S04 | The negotiation interval for a target month is inclusive from exactly seven 24-hour days before its UTC start through seven days after. Key validity is still month-specific, not extended by that window. | `negotiationWindow` |
| S05 | A recipient holding an old key can still decrypt old ciphertext; rotation does not revoke already known content or keys. Group key possession does not authenticate a unique publisher. | old-key and tamper tests |
| S06 | Composed publisher subscriptions sign channel, epoch, message ID and text, then encrypt the signed envelope under the current monthly key. Opening requires the configured publisher signature and an exact match of inner and outer channel, epoch and ID. Knowing the group key alone cannot impersonate the publisher or rewrap a signed message into another scope. | `sealPublisherMessage`, `openPublisherMessage` |

`publisherMessage` provides public signature verification, and ordinary symmetric messages allow any group-key holder to author valid group ciphertext. `MonthlySymmetricChannel.sealPublisherMessage(text, messageId, publisherIdentity, now)` composes both mechanisms: it signs the complete subscription scope then AES-GCM encrypts the signed envelope with the current monthly key. `openPublisherMessage(envelope, expectedPublisher)` decrypts, verifies the explicitly configured publisher, and checks inner/outer scope. A subscriber can decrypt or create group ciphertext but cannot forge the publisher signature. The 64 KiB encrypted plaintext limit includes the signed JSON envelope, so the composed text limit is lower and depends on JSON encoding overhead.

Production payment negotiation, key delivery, purchase-based access control, revocation and publisher discovery are not implemented. The dummy subscription adapter below tests a settled-credit gate before releasing a `dummy:` token; it does not distribute a real monthly decryption key. The negotiation function is a calendar predicate, not an enforced payment gate. Local key storage is memory-only, with no secure deletion guarantee. The examples use text only; images/video remain future work.

Authenticated encryption and publisher signatures alone permit replay of unchanged messages. Production clients need bounded application-level duplicate handling tied to their transient retention policy. The subscription tests explicitly demonstrate repeated decryption, so this limitation cannot silently become a claim of replay resistance. Random AES-GCM nonces have a collision bound; production must choose volume/key-lifetime limits and avoid multi-process nonce misuse. These modules do not implement traffic-analysis resistance, anonymous key delivery, mix routing or unlinkability.

## Application settlement contracts

The owner distinguishes three uses: advertising rewards for agreed actions, voluntary creator support through superlikes/donations, and subscriptions in exchange for verified funds. A signed promise is not a payout. `DummyUseCases` preserves these distinctions instead of granting a generic entitlement for every signed claim.

| ID | Contract | Executable surface |
| --- | --- | --- |
| U01 | Receiving a signed transfer stores only a pending promise and creates no balance. Explicit authority settlement consumes live provenance and creates recipient outputs; unfunded or invalid promises cannot settle. A settled promise may subsequently be spent, so its status is not a current balance assertion. | `receivePromise`, `settlePromise` |
| U02 | A superlike redemption binds the target post and creator key. Invalid, unfunded, expired, wrongly targeted or already-spent claims degrade to an ordinary like. Both outcomes have ranking weight 1 and no access entitlement; no balance/wealth metric is exposed by this adapter. | `superlikeService`, `redeemSuperlike` |
| U03 | Advertisers sign a campaign action digest, budget and expiry. Collected proofs bind the exact campaign, agreed action, recipient, advertiser offer and recipient-signed evidence claim; collection alone transfers nothing. | `registerCampaign`, `advertisingRequirement`, `collectAdvertisingProof` |
| U04 | Redeeming a collected proof transfers only verified advertising units, once per campaign action/recipient, without exceeding the campaign budget. Exact retries do not pay twice. Competing claims serialize within this adapter. Claims authenticate agreed action/evidence assertions, not human attention. | `redeemAdvertisingProof`, `campaignStatus` |
| U05 | A subscription payment binds product, UTC month and creator, requires exactly the configured price in settled ordinary credits, and consumes it before releasing a `dummy:` token. Pending promises, wrong purposes, expired funds and advertising currency cannot release tokens. | `registerSubscription`, `subscriptionService`, `releaseSubscription` |
| U06 | Capacity checks, credit acceptance and dummy token release are synchronous within one process. Exact payment retries return the original token without another debit/slot; competing requests for the last slot debit/release at most once. Self-tipping cannot create new issued or withdrawable units. | `subscriptionStatus`; delayed-settlement, capacity-race and self-tip tests |

`redeemSuperlike(target, creator, signedRedemption, now)` represents creator support as an attributed **dummy service redemption**. The underlying authority removes those units from circulation; it does not credit a creator wallet or make a real payout. The same limitation applies to subscription redemptions. Payout eligibility comes only from verified settled units, and the test suite never mints new value in response to a promise or self-tip. Actual creator payout accounting and delivery remain unimplemented.

`registerSubscription` is trusted local setup, including the creator key, and accepts only configured `dummy:` tokens. Products are not creator-signed, and product IDs share one namespace per epoch. A remote creator API would require creator-signed products keyed by creator. The adapter verifies the payer signature, but has no authenticated caller session or encrypted response-delivery channel; this is not secure real key delivery. Monthly epoch binding is tested, but monthly negotiation and encrypted channel modules are not connected to the token adapter. Production must compose recipient-authenticated delivery with durable settlement, recovery and revocation policy before releasing real keys.

The campaign flow is closed only while the authority is reachable exclusively through the advertiser-operated adapter. Campaign budgets are ceilings, not reserved escrow. Payment still fails if the advertiser's signed input has been spent elsewhere. Participant uniqueness is per key within one campaign action, not a human-identity or anti-Sybil guarantee. A participant or advertiser controlling both endpoints cannot increase total issued supply. The advertiser controls agreed requirements and collects the proofs; the adapter provides accounting checks without claiming advertising effectiveness. All campaign redemptions must enter through this adapter for its aggregate budget/recipient checks to apply; calling the lower-level authority directly or starting another adapter does not enforce shared campaign state.

The application adapter stores at most 1,024 records in each promise, campaign, collected-proof, subscription and purchase collection. Exceeding a limit fails closed. These local bounds are not network rate limiting. Settlement/redemption/release calls also enforce a nondecreasing trusted timestamp before validation, so a rejected expired campaign cannot be revived by rolling application time backward. All records and decisions are memory-only and require a single trusted owner. A crash between external settlement and delivery is outside this model: production needs durable transactions and an idempotent outbox/recovery protocol. The tests use local synchronous races and dummy tokens, never funds or real entitlements.

## Validation and efficient progression

The tests cover forged signatures, wrong owners, domain substitution, malformed keys/amounts, unknown fields, duplicated provenance, 47→50 overspending, atomic competing spends, lost-response retries, conflicting IDs, double redemption, inherited expiry, signed ad offer/claim binding, claim replay, currency separation and per-step supply conservation. A fixed-seed 600-operation adversarial run is reproducible. Tests also demonstrate the limitations of independent authorities, old-key revocation and cryptographic message replay prevention.

Operations cost O(number of consumed and created outputs), bounded to 64 inputs/outputs per transfer. Idempotency and spent provenance decisions require retained state: this model does not prune it. Issuer and claim records are unbounded; production needs explicit retention, durable checkpoints and abuse budgets before accepting untrusted traffic. Tests run without external providers or spending. Installed PACT/Constrain checks are reported separately; these tables are testable specifications and are not claims that a named tool has run or proved the system correct.

Next material decisions are durable finality and trust distribution; unlinkability mechanism and adversary model; evidence verification and privacy cost; offer reservation/failure policy; fee/conversion/rounding schedule; epoch key delivery and revocation policy. Establish these before any live funds or backend integration. Recovery for this sandbox is to rerun deterministic tests from source, never to treat discarded in-memory balances as redeemable state.
